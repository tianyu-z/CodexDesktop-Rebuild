# 远程项目的 Codex / Claude Code 模式

日期：2026-09-27。状态：设计草案，按用户“与 Codex 使用相同远程原理”的要求修订；应用层尚未实现或安装。

基础：[现有模式设计](2026-09-27-codex-claude-conversation-modes-design.md)；实测结果：[远程验证记录](../../remote-claude-validation.md)。

## 使用方式与范围

沿用客户端现有远程项目：用户打开 rno 等集群上的目录后，可在该聊天中选择 Only Codex 或 Only Claude Code。执行引擎和文件工具都在所选集群的该目录运行，历史留在同一个聊天中。切换引擎不切换主机，也不创建另一条可见聊天。

这是对原有适配器架构的扩展。首批验收 rno、bar、ala、blc、blc-2、sko；其他别名在 SSH 连通并通过能力探测后采用相同方式。Codex + Claude Code 继续保留为禁用模式。本阶段不增加一条本地聊天同时调度多个集群的能力。

## 方案选择

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 在集群运行网关，沿用 SSH / WebSocket 连接，集群直接访问其已有 API 代理 | 与现有 Codex 的远程执行和 API 网络路径一致；复用远程目录和历史文件；便于以后扩展两种引擎 | 需要管理远程运行时、连接恢复和按主机的能力检查 |
| 在本机运行路由器，逐个 SSH 转发 Claude 进程及文件操作 | 集群部署量较少 | 现有路由器的目录校验、历史文件和上下文交接都需跨主机适配；本地状态与远程执行更难保持一致 |

采用第一种作为目标。重新检查 rno 的实际 Codex 配置后确认：远程 Codex 使用集群内的 Foundry 代理和配置中的请求头，不依赖 Mac 的模型 API 连接。复用该集群配置并使用同源的 Anthropic 路径，远程 Claude 已真实调用成功。

此前的本机反向转发只是临时验证路线：测试把 Mac 的 Foundry 地址用于远程环境，导致 DNS / 认证失败，不能由此推断集群必须经过 Mac 才能调用 Claude。默认方案不建立本机 API 转发器；本机仅通过 SSH 发送控制消息并接收结果。若某个主机没有可用的远程提供方配置，明确报告配置问题，后续再按用户选择增加可选转发。

## 组件与数据流

1. **桌面连接管理。** 复用已保存的 SSH 别名、端口、身份和配置。连接时探测 Claude、Node、Codex 协议能力，并按应用版本校验远程网关。安装只进入用户拥有的独立版本目录，保留旧版本用于回退。
2. **远程传输。** 为网关提供独立且仅当前用户可访问的 Unix socket，通过原有 SSH 通道承载 WebSocket。网关作为原生远程 Codex App Server 的客户端；不占用其标准 socket，不新增杀死或替换原生服务的操作。普通 Codex 请求继续转交原生服务。
3. **远程引擎网关。** 复用 EngineRouter 和官方 Claude Agent SDK，调用集群实际安装的 Claude。根据 Codex 能力采用完整历史或分页接口。统一历史、引擎绑定和交接文件都写在该集群的独立用户目录。
4. **连接配置。** 明确配置的远程 Claude 提供方优先。针对已验证的集群 Foundry 网关，可从远程 Codex 的实际提供方配置读取同源 API 地址、静态请求头及其环境请求头映射，在内存中形成 Claude 的连接环境；只在已确认支持 Anthropic 路由的同一服务使用现有认证，不把凭据发给其他主机。凭据不写入安装包、日志或聊天记录，不改写用户已有配置。传输或认证故障显示具体原因，不静默回落到本机执行或本机 API 转发。
5. **前端。** 能力与会话缓存均以 host ID 为作用域。远程项目只有在相应主机能力握手成功后才显示可用的 Claude 选项；引擎来源标记、审批、中断和忙碌时禁用选择器沿用现有交互。主机不可用时保留原有连接错误。

目录归属始终由远程项目确定。客户端不把 Mac 路径当作 Linux 工作目录，也不根据名称把不同 SSH 别名的会话合并。

## 恢复与边界

- 网关独占自己的存储目录；同一应用配置的重复连接不可启动第二个写入者。
- 每个线程最多有一个执行中的轮次；所有权限回复绑定线程、轮次和请求 ID。恢复连接不得自动批准或重复执行工具。
- 远程网关独立于桌面 SSH 连接驻留。仅控制连接丢失时不主动终止 Claude 轮次，模型和工具继续在远程进程内运行，公开输出写入远程存储；桌面重连后通过线程读取同步状态，不自动重放轮次。待人工审批的请求仍保持未批准，重连后重新展示相同请求 ID；只有用户明确中断才取消正常运行。需要为暂时无控制端连接时的输出及挂起审批实现有界缓存和恢复测试。
- 网关崩溃或重启时，将未完成的 Claude 运行恢复为已中断。正常轮次之间可恢复同一原生 Claude session。
- 认证或运行时准备失败时显示具体错误；已进行的聊天不被替换为新聊天。升级仅影响独立网关目录，可回退而不删除任何引擎的历史。
- 不支持的双引擎、跨主机迁移、混合历史分叉/回滚保持明确不可用。

## 实现步骤与验收

1. 增加远程传输、网关握手及存储锁，覆盖请求 ID、重复连接、错误清理和旧 Codex 历史协议。
2. 增加桌面端运行时准备与远程提供方解析，覆盖请求头映射、SSH 断线、凭据轮换和进程退出，不记录凭据。无需创建本机 Foundry 转发端口。
3. 将前端选择器和元数据缓存扩展到 host ID，测试不同主机同时开聊天不会串用能力、模式或模型。
4. 在 rno 的一次性项目中，通过实际客户端界面验证 Claude 回复与远程文件读取，再验证 Codex → Claude → Codex 的双向上下文。
5. 验证远程写操作允许、拒绝、待审批时取消，以及控制连接断开后远程执行继续、重连后补齐输出与审批。拒绝/明确取消后目标文件必须不存在，且无遗留的自有 Claude 进程。控制连接丢失不得被混同为用户取消。
6. 重启客户端和网关，验证聊天历史、引擎选择及 Claude session 恢复；在其余五个连通集群重复主要调用和文件测试。
7. 复测现有本地模式及原生远程 Codex，使用独立预览应用验证后，再备份并更新安装版。

当前通过的是底层远程 Claude 调用、文件读取和 rno session 恢复。以上应用层验收尚未开始。
